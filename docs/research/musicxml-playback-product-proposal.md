# MusicXML 播放：产品与交付方案

日期：2026-09-15。状态：建议方案，未实施、未变更 ADR、未迁移生产数据。

## 决策摘要

Same Page 增加「可播放乐谱附件」，支持 `.musicxml`、`.xml`、`.mxl`。复用 Chorus 的 alphaTab 播放实现与音乐语义修正，提取一个有版本的播放器模块。Chorus 保留独立产品和部署；两者不在运行时互相调用，不共享登录、数据库或用户文件。暂不合并仓库，不创建第三个产品或远程播放服务。

上线的完整用户任务是：上传一份可播放附件，选择声部和速度，播放并可回到所属 PDF 继续阅读。只有附件大弹窗、关闭就不能练习的体验适合内部原型，不作为最终交付。

## 依据与实测范围

- Same Page 的 `CONTEXT.md` 将 Score 定义为稳定身份的 PDF 谱面及笔记集合，附件依附 Score；此次保持该身份与 PDF 版本、批注坐标语义。
- `docs/operations/score-attachments.md`：附件目前在线使用，同源鉴权读取；已有上传预留、配额、不可变对象、回收站和清理队列。
- `src/shared/attachments.ts` 的四种类型枚举、`use-library-attachments.ts` 的整批解析，以及迁移 0027 的 SQL CHECK，需要一起考虑新增类型兼容性。
- 同级 `../music-ocr/package.json` 项目名为 `chorus-score-studio`，使用 alphaTab 1.8.4。`src/main.ts` 为 2,892 行，混合播放器、DOM、房间、目录、OMR 入口和导航；不能直接作为嵌入接口。
- 已有 `musicxml-direction-timing.ts`、`alphatab-playback-dynamics.ts`、`practice-mix.ts`、`timbre-profile.ts`、`playback-measures.ts`、`score-follow.ts` 可复用。音乐语义应由既有真实导入/MIDI 测试保护；`player-contract.test.mjs` 中的源代码正则检查不足以证明提取后实际播放正常。
- 2026-09-15 只读统计本地 21 份 MusicXML：按原始大小排序，中位文件 458.2 KiB，gzip 后 11.6 KiB；最大文件 1,250.2 KiB，gzip 后 43.8 KiB。这是压缩实验，不是 MXL、HTTP 或设备播放性能实测。
- 已有 dist 中主 JS 约 1.3 MiB，worker/worklet 各约 1.1 MiB，音色目录约 2.2 MiB；构建产物可能不是当前源码最新构建，磁盘值不能相加解释为实际网络传输量。
- 格式标准及引擎源码核实见 [格式研究](musicxml-format-and-playback-evidence.md)。

## 产品定位

### Same Page

以云盘中的 PDF 和排练笔记为中心。「播放」是这一份谱的练习能力。MusicXML 存成附件，不取代 PDF、不把所有文件库对象泛化成任意格式文档。

首版路径：

1. 在添加附件中选择「可播放乐谱（MusicXML）」，选择三种扩展名之一；格式判断由程序完成，用户不需要理解压缩。
2. 上传前本地快速检查；上传成功代表文件已保存，不能伪装成全部音乐内容已校验。
3. 点击附件进入练习面板，显示文件名、声部、准备状态；用户主动播放，上传完成不自动发声。
4. 提供播放/暂停、速度倍率、声部独奏/静音/音量、关注声部、小节定位；A–B 小节循环属于首版练习闭环，需要新增可靠 UI 和回放测试。
5. 可展开 MusicXML 自身的交互谱面，也可选择「看原谱」进入所属 PDF，保留同一个播放会话。
6. PDF 中只有已主动打开播放会话时才出现紧凑控制；可收起详情，仍可暂停、回到控制面板、结束播放。此时可手动翻页，不承诺 PDF 自动跟随。

紧凑控制属于用户主动开启的练习模式。它需要调整 ADR-0010 对始终显示阅读控件的排除规则：默认阅读继续沉浸，活动播放会话允许最小控制。不应在实现中偷偷改变既有 ADR。

生命周期明确区分：收起详情不停止；结束播放销毁；离开所属谱/云盘、切换用户、退出、已知权限撤销会停止并释放。当前云盘列表进入同一份 PDF 是保留会话的显式导航。初版不做全站播放队列，不在另一个无关乐谱上继续播放前一首。已有原生音频附件与 MusicXML 互斥发声，先做少量协调，不借机重写成通用媒体平台。

选择声部、速度和位置是个人练习偏好，不写回原谱、不改变其他成员。首次实现本机保存，按本机身份、云盘、附件及内容版本隔离；新内容不能误用旧轨道索引。首版不做云端练习状态同步。

### Chorus

独立定位为打开 MusicXML 即可练习的轻量播放器，支持本地导入和现有曲库入口，不强迫用户先上传 PDF 或创建云盘。

保留已有房间、会话、曲库、URL、OMR 入口和数据；本次不迁移、不删除、不复制到 Same Page。播放器迭代集中在共享模块，Chorus 专有外壳做必要维护。是否将来停掉 Chorus 应由独立入口使用量和维护成本决定，不能成为此次交付前提。

## 文件策略

| 层次 | 建议 |
| --- | --- |
| 用户输入 | 同时接受 `.musicxml`、`.xml`、`.mxl`；XML 必须确实为 MusicXML |
| 云端权威文件 | 保留上传原字节，下载原文件；不重写、自动修谱或强制改成另一种格式 |
| 原始配额 | 按保存的原始对象实际字节计量，沿用附件配额 |
| 运行时 | 在受限处理流程中解包、解码为内部 UTF-8，再执行针对引擎的内存修正 |
| 当前生成文件 | 无需新增导出转换功能；将来系统生成 MusicXML 时优先输出标准 `.mxl` |
| 传输优化 | 未压缩 XML 可另行验证 HTTP 内容编码；MXL 本身已压缩，不重复压缩，不把边缘自动压缩当成已验证能力 |

MXL 是 MusicXML 的标准 ZIP 容器，不是质量较低的格式。优先支持它能避免要求用户为了上传另行重新导出。压缩减少存储与传输，不减少解压后的谱面复杂度。

建议首版范围：MusicXML `score-partwise`，UTF-8 和带明确 BOM/编码声明的 UTF-16；未知或冲突编码给出明确导出建议。已核实 alphaTab 1.8.4 同时实现 `score-timewise`，但 Chorus 时序与力度预处理只遍历 partwise。因此首版识别 timewise 并清晰提示支持范围，不承诺与 partwise 等价的音乐行为，也不临时写未经验证的格式转换器。`opus` 乐谱集同样不在首版范围。

初始上限建议：原文件 20 MiB，选定的解压 XML 同样最多 20 MiB。还要限制容器条目、元数据、解析深度和工作时长；最终复杂度预算由真实谱压力测试确认。压缩后小不等于可无限解析，不能只检查 ZIP 声明的长度。

解包按 `META-INF/container.xml` 选择乐谱入口，只展开所需文件；拒绝加密、异常路径和损坏容器，不递归解压，不执行/展示附带脚本和 HTML，不获取外部 DTD、实体或图片。常见标准 DOCTYPE 可忽略外部引用，不应一律误报。使用维护中的 ZIP/XML 库及实际输出字节限制，不手写解压算法。不要直接使用一次性解压全包的便利接口处理不可信 MXL。

## 播放正确性与失败定义

格式有效、当前引擎可播放、音乐内容与原谱一致，是三个不同结论：

- 不合法容器/XML：拒绝并指明原因。
- 有效但不在支持范围：新上传在预检查/准入时清楚提示并拒绝，不把它称为损坏；若已保存的文件在当前播放器版本不能打开，保留原文件与下载能力，不自动删除。
- 能导入但发现影响音高/时序的已知问题：有具体提示，不能用“导入成功”掩盖；文件存储状态与播放可用性分别显示。
- 音色准备失败或浏览器未允许发声：保留附件与可用谱面，提供重试/点击启用声音。
- 不宣称演唱歌词、出版级排版、自动识别 PDF、自动与原 PDF 对齐。

声部控制以引擎实际可独立播放的轨道为准，沿用原名称。同一 staff/part 内的多个 voice 不能仅凭 SATB 名称自动当成独立轨道；无法分开的内容应明确呈现。识别不明的轨道保留原音色，避免把伴奏自动变成人声。

当前 `main.ts:1750` 的通道分配在 15 个非打击乐 MIDI 通道之间取模循环；超过此数量会复用通道，且该分配没有按打击乐轨道分类。开放任意用户附件前应验证多轨混音和打击乐语义；无法安全独立控制时明确限制支持范围，不能仅因精选合唱曲库正常就宣称任意编制支持。

调速使用相对倍率，保留谱内速度变化；循环使用明确的时间/小节实例身份，考虑弱起、重复编号、反复和房子，不能只以可见的小节数字作为唯一键。

## 实现与代码归属

先在 Chorus 仓库创建 `packages/player`，Chorus 直接消费；Same Page 消费同一模块的固定版本发布包。保留两个仓库、CI 和独立部署，不使用生产相对目录引用，不同步复制源码，不在线加载浮动 `latest`。发布包只含播放器代码和所需静态资源，不包含私有乐谱、房间配置、凭证或部署脚本。

模块内部保留 alphaTab 1.8.4 及现有兼容修正。提取期间不同时升级引擎，也不重写整套 UI 框架。Same Page 的 React 只作生命周期和状态适配；原有播放器 DOM 实现必须限制在显式宿主元素内，清除全局选择器、固定 ID 和全局快捷键泄漏。

外部 interface 应表达：加载原始内容/取消、播放暂停、定位、速度、混音、循环、读取状态/订阅，以及释放。可选谱面视图挂接同一播放会话。外部不暴露 alphaTab Score/Track 对象、内部事件顺序或引擎修正规则；不设计多引擎插件体系。具体类型在纵向原型后固定，避免凭空制作庞大 SDK。

Same Page 拥有：鉴权读取、身份与内容版本、附件存储、下载、导航、会话存续、偏好持久化、产品外壳。播放器拥有：格式准备、导入、音乐修正、合成、谱面与时间轴、小节及混音状态。Media Session 与音频焦点由宿主协调，避免两个来源抢占。

原始文件 → 必要解包和编码归一化 → 引擎适配修正 → alphaTab → MIDI/音色播放。修正结果只在内存中；不持久化 alphaTab 内部模型。首版也不持久化 MIDI/渲染缓存。将来确有需要，派生缓存以原始文件身份、播放器版本、归一化版本为键，可随时失效重建，不能成为新的权威源。

## 服务端与发布兼容

服务端延续现有上传预留和不可变 R2 对象流程，加入受资源限制的容器/编码/结构准入检查；客户端检查不能成为服务端信任依据。完整排版、音色、MIDI 准备放在浏览器，不引入服务器合成和转码队列。

需要用实际部署计划验证服务端结构检查的 CPU/内存预算；不要把 20 MiB XML 一次构建成几个完整树再与音频上传共用执行路径。Cloudflare 当前每 isolate 128 MB 限额，且并发请求共享它，见 [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)。若同步准入检查不能稳定达标，应调整流式验证方式/限额或单独立项受限处理流程，不能上线依赖前端预检查的假验证。

兼容协议推荐新客户端显式请求扩展附件协议版本。未声明的旧客户端继续收到原有四类型；列表、回收站、恢复响应及相关附件数量必须一起审查。未来客户端逐项处理未知类型，而不是整批失败。MusicXML 功能上线前提供受控开关。

SQLite CHECK 扩展要设计新迁移，不修改已执行的 0027。若需要重建表，必须保留附件/文件 ID、外键、索引、引用和清理/配额触发器，验证不会重复扣加用量或触发对象删除。使用含实际旧状态的迁移夹具验证，包括待上传、回收站、删除队列。

顺序：安全数据库迁移 → 默认保持旧契约的兼容服务端 → 支持新协议的客户端 → 小范围启用 MusicXML → 观察后放开。回滚关闭新上传/播放器入口并回退代码，保留新附件原文件与用量；应有支持新类型下载的救援版本，而不是要求旧代码理解新类型。不得通过删除数据回滚。

## 性能与设备策略

- 文件库/PDF 普通访问不加载播放器 JS、worker、字体或音色；也不进入默认 PWA precache。
- 用户进入播放时并行准备模块、文件与音色；播放由显式用户手势触发，在手势处理阶段处理音频解锁。
- 同一标签页最多一个活动播放会话。收起详情不重新解析/加载音色；结束时解除所有事件、音频、worker 和 DOM 引用。
- XML 解压/预处理等可独立工作移入 Web Worker。当前同步 alphaTab 导入是否能迁移、模型如何交还必须原型验证，不能假定存在 worker 就没有主线程开销。
- 可播放状态与谱面显示状态分开；避免为“听”等待整个谱面排完。具体解耦方式先用既有引擎路径验证，不为此马上自建底层合成引擎。
- 同源版本化音色与字体；不因跨产品共用代码而运行时向 Chorus 请求资源。
- 首版承诺联网打开，已完整加载后的短暂断网可继续当前会话；不等于刷新后离线可用。暂不增加附件离线副本承诺。
- Media Session 是系统媒体控制集成，不保证 iOS 锁屏/后台 Web Audio 持续运行。首版以页面前台练习为验收，遇到系统暂停保留状态并可继续，不循环强行恢复音频。

性能记录：点击至反馈、文件准备、解析、音色就绪、首个可见谱面、首个可听声音、主线程长任务和多次开关资源趋势。样本含小型 SATB、长作品、多 voice、复杂反复、大型 MXL。按固定网络条件和真实最低目标 iPad建立预算，分冷/热加载报告；本文不提供未经测量的秒数保证。

## 交付分段及退出条件

1. **一个纵向验证分支**：真实 MXL → 准备/修正 → 播放 → 关注声部 → PDF 紧凑控制 → 结束。先验证复用 interface、音频解锁、引擎与视图生命周期、构建及 worker 资源路径；暂用固定测试数据，不改生产表。这不是可发布的完整功能。
2. **提取与回归**：把纵向路径整理成最小共享模块，Chorus 改为消费；保证旧房间/导入/音色/定位行为回归。不要以“完成所有播放器重构”为起点无限延伸。
3. **附件与兼容交付**：类型、结构检查、上传/配额/清理、协议与迁移、实际云端文件、UI 和个人偏好。完成端到端上传至练习。
4. **练习与设备验收**：分声部/调速/循环、PDF 返回、音频互斥、错误恢复、关闭释放、权限与身份变更；真实 iPad Safari/PWA 和 Android 验证。
5. **分阶段发布**：先少量实际使用者与真实谱；比较失败原因、首次可播放时长、打开到播放转化及重复使用。诊断只记录版本、耗时、数量和错误类别，不上传谱面正文/歌词/凭证。

### 必须通过的检查

- 同内容 XML 与 MXL 产生等价的音符时序、速度和轨道；原始下载哈希不变。
- 弱起、延音、变拍、divisi、多 voice、反复/房子、渐强减弱、速度变化；既有力度/音色 MIDI 断言保留。
- 损坏容器、超限解压、异常 XML、错误编码、无法支持的根类型均可控失败。
- 播放面板开关、PDF 之间的显式切换、快速连续换附件、音色失败和重试、网络中断不制造重叠音频或迟到结果。
- 旧客户端在新附件存在时仍可读原类型，列表与回收站不整批报错；迁移前后配额和引用不变。
- 新功能不改变普通 PDF 的加载资源和阅读输入行为；反复打开关闭没有累积音频会话。
- 桌面模拟、自动化通过、真实设备通过分别报告。播放听审不能由解析成功和源码正则断言替代。

## 明确推迟的能力

PDF 自动识别为 MusicXML、PDF 跟随对齐、MusicXML 编辑/版本协作、所有文件都变成独立主谱、云端音频预渲染、整套离线练习下载、全站播放队列、跨设备练习同步、任意 voice 自动拆 SATB、无限制大谱和所有 MusicXML 元素完整兼容。

这些能力不作为播放器首版依赖；后续按实际使用需求独立决策。
