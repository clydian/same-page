# 可选播放器加载失败与部署更新

历史问题 #446：旧页面可能一直保留旧版应用壳；当时播放器是按需下载的模块，且有意
不进入 PWA 预缓存。2026-10-28 起完整播放器随应用壳预缓存，见 ADR-0020 的必需离线播放修订。旧部署方式替换哈希文件后，旧页面首次打开播放器可能请求
已经不存在的旧模块。当前 ADR-0021 使用不可变 `/_releases/<sha>/` 归档，
旧页面仍可读取自身版本的模块；发布新版本本身不应禁用播放器。安全更新会保留仍在工作的页面，并允许其他窗口否决切换，
不能用自动刷新或清空站点数据处理这个失败。

播放器区域现在有独立错误边界。模块加载或播放器渲染失败会切回 PDF，保留
阅读器、笔记编辑器和全局更新监听。错误区显示更新检查结果，提供关闭播放器、
恢复播放器、检查更新和关于合谱入口。恢复当前页面无需等待新版本，详见下文。
检查只准备更新；完成当前操作后，用户仍通过关于
合谱的既有安全交接应用更新。其他窗口否决时继续保留当前版本。

`assets`、`pdfjs`、`font`、`soundfont` 四个静态资源目录通过 Worker 的 ASSETS
绑定读取。真实资源保留原字节、MIME 与缓存头；缺失响应或 SPA 回退 HTML
转换为 `404 + Cache-Control: no-store`，不再将 HTML 按模块 URL 缓存一年。
正常页面导航仍沿用 SPA fallback，API 路由不变。代价是这些目录的请求增加
一次 Worker 调用。这是 #446 当时的保护措施；当前旧构建资源托管由 ADR-0021 的发布归档提供，完整播放器现已纳入应用壳安装校验。

已运行的旧客户端仍须按原更新流程切换后才能获得错误边界。这个补丁不能
热补已经加载的 JavaScript，也不能收回浏览器此前缓存的旧模块 URL 响应。

回归：`playback-gate.test.tsx` 拒绝实际 lazy import，确认未保存输入保持同一
DOM 和内容、回到 PDF、可见更新反馈及可关闭。`static-assets.test.js` 覆盖
HTML 回退、404 缓存头和真实文件透传。真实 Chromium/WebKit 的
`playback-load-failure.test.mjs` 从成员阅读器打开附件，注入相同 HTML/MIME
加载失败，确认 reader 根节点/PDF 未卸载、检查更新不导航，并通过实际本地
HTTP 验证四个目录的缺失资源和正常 SPA/脚本响应。桌面 WebKit 不代表真实
Safari/PWA 验收；原多窗口 PWA 更新测试继续保护交接策略。

部署后核对旧 `/assets/musicxml-player-BRJQwkJT.js` 返回 404/no-store，当前
build.json 中的脚本仍返回 JavaScript/immutable，再从成员附件入口实测播放。
不要通过清站点数据、强行激活 worker 或关闭其他使用中的窗口绕过安全策略。

## 慢网络与准备反馈

前台准备依次确认访问权限、读取本机缓存（250ms 预算）、必要时下载乐谱原件，
再由 Worker 处理乐谱、建立模型、生成播放数据。音色加载和谱面排版可与后半段
并行；界面只显示当前仍在等待的阶段，不把并行工作编造成固定步骤百分比。
下载进度使用已授权附件大小和实际接收字节；音色进度使用引擎的实际加载事件。
处理、生成和排版没有可靠工作量时使用不确定进度。可播放且首个谱面可读后，
离线保存才在后台启动，不阻挡播放。

附件读取与引擎准备各自有 180 秒上限（原为 60 秒；两段最坏可累计约 6 分钟），
明确网络或解析错误仍立即反馈。单阶段持续 30 秒后提示可继续等待，并提供显式
重试；重试中止旧读取、销毁旧引擎，晚到的完成事件不能恢复失败或已关闭的任务。
不无限延长等待，也不自动重复下载。

播放器模块加载失败与上述准备超时不同。错误边界保留阅读器及未保存内容；
提示检查网络，持续失败后通过关于合谱的安全流程检查版本。React.lazy 和浏览器
都可能记住失败的模块加载，单纯重建 lazy 包装不构成可靠恢复，不能用一个无效
重试按钮掩盖这个限制，更不能在阅读器中强制刷新或清理数据。

回归覆盖 61 秒后仍可完成、180 秒截止、晚到事件、真实下载/音色进度和重试取消。
`visual-report/playback-preparation.test.mjs` 在 Chromium/WebKit 手机尺寸下，
从成员附件入口打开真实播放器，暂停原件下载检查阶段及截图，再放行直到可播放。
这不等同于真实 iPhone 弱网及后台恢复验收。

## MusicXML 打开任务归属

`musicxml-opening.ts` 拥有一次练习播放的权限复查、更新保护与资源释放；
`musicxml-player.tsx` 只挂接谱面、展示快照并转发用户动作。source resolver
继续负责原文选择、修订校验与本机身份／清理 fence，不改变存储格式。

打开重试取消旧读取、旧权限检查和旧离线任务，释放播放器与准备结果 lease，
再创建新尝试；离线准备重试保留当前播放器、位置与已下载字节。读取超时
不终止后续 focus 权限复查。切换播放内容或结束练习立即释放旧 owner，
旧尝试的迟到结果不能停止新会话。离线准备失败不终止已可用的播放。

`musicxml-opening.test.ts` 通过打开 interface 验证超时、重试、权限与引擎事件
的组合；`musicxml-cleanup-intent.test.tsx` 使用真实本机存储规则验证自动任务
不能复活已清理文件，以及明确重试建立新写入意图的顺序。

## 模块失败后的持续报错与安全恢复

已在生产构建复现：播放器模块首次返回一次 404/no-store，资源恢复后，关闭再打开
仍立即失败，模块请求计数没有增加。顶层 `React.lazy` 保留失败 Promise，重挂错误
边界不会重新导入。WebKit 还会保留失败的 `modulepreload` 资源，导致刷新或经过
其他页面后仍不重新请求。与 WebKit #270357 的失败内存缓存机制吻合：
<https://bugs.webkit.org/show_bug.cgi?id=270357>。上游主干修复不代表所有已发布
Safari/iOS 都已经包含；桌面 WebKit 复现仍不等同于特定用户 iPhone 的首因证明。

构建仅对 `musicxml-player-*`、`audio-player-*` 动态入口的 JavaScript 依赖关闭
Vite modulepreload，改由原生模块导入加载；Vite 的 CSS 预加载以及应用壳、其他
路由的预加载保留。这样避免可选播放器图的预加载失败跨页面持续卡住。代价是
冷启动时可能增加原生模块的依赖发现等待，不改变播放器的按需运行；其资源现随应用壳预缓存。
这是构建层规则，不按浏览器 UA 分叉，也不向模块 URL 拼接重试参数或混用新旧
版本模块。

错误区的“恢复播放器”通过既有 `afterEditing` 完成本机保存和离开确认，取消或
保存失败时保留原阅读器。进入关于页恢复区后，用户还需明确点击“重新加载页面”。
`ShellRecovery.requestReload` 沿用安全路由、本机任务、对话框、可见性与
输入焦点门禁；离线时额外核实本机请求版本与 active 壳完整性，未确认则明确提示联网重试，只恢复此页面，不请求激活 waiting worker；候选版本的自然生命周期
仍由既有发布许可和多窗口协议约束。显式操作无需等待新版本，也不清站点数据。
自动 lost-shell 恢复仍要求已验证替代壳及每目标一次的防循环记录；显式恢复每次
需要用户操作，本页面内执行一次，不依赖 sessionStorage。恢复实例独立于 SW
注册重试，等待中的请求不会因注册失败重试丢失。

现有诊断格式中，模块导入失败记录为 `request / attachment-entry`，保留可识别的
cause 类型；组件渲染失败仍是 `decode`。只使用既有字段及枚举，不扩大上报为任意
错误字符串、资源 URL、乐谱或笔记。该区分不能反推出用户历史首次请求的 HTTP
状态；旧无版本 URL 404、传输失败及访问拦截仍需具体请求证据区分。

回归采用真实 `/_releases/<sha>/` 生产构建，Chromium/WebKit 分别覆盖 XML 入口、
引擎静态依赖、音频入口 404 以及 XML 入口网络中断：资源恢复后同页面失败仍可复现，保存后进入恢复区
本身不重新加载，显式请求才重新加载，随后重新请求模块直到可播放，并检查样式
仍加载。已运行旧客户端需要按既有安全流程更新后才能获得此规避，不能热补已经
在浏览器里失败的旧模块图。

生产视觉测试复用独立构建/预览夹具，隔离输出目录、player workspace 和可写的
构建缓存，避免并发测试互相替换版本前缀与资源哈希。两个文件以 CI 的并发方式
共同验证，而不是通过全局串行化规避冲突。
