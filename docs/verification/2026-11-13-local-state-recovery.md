# 本机检查卡住与保存目录的失败处理 · #651

## 已知与未知

用户报告更新后打开谱子久停“PDF 已就绪，正在校验本机状态”，返回后离线列表像是空了；另有身份功能表现为离线，连接探测仍可连接。尚无本次设备的诊断报告，不能断言由更新引起，也没有证据证明文件被删除。

定位到提示对应 ReaderSession 的 PDF 完成后 owner/session epoch 检查，已不是 PDF 网络下载阶段。只读查询生产诊断收件箱没有找到本次对应的新报告，未写入生产数据。

在隔离 fake IndexedDB 中，原实现遇到临时 Blob 读取异常时，三首保留谱全部被列表过滤；offlineScores 和 offlineSnapshots 各仍有三条，读取恢复后可再次出现。另以受控 pending 检查复现 PDF 已解析而 local-check 不结束；取消没有删除文件/快照。这些证明具体失败处理问题，不证明用户设备的底层存储为何迟滞。

## 本次修复的边界

- 保留目录沿用 LocalLibrary 的导航语义，只读取当前 owner 的保存元数据，不为列目录逐份读取/hash PDF。显示入口不等于宣称副本已校验：离线徽标和实际打开仍验证当前字节及笔记快照。
- 临时目录读失败保留已显示内容并提示重试；owner fence 变化仍清除旧身份显示。错误作用域的记录不列出，原始文件不删除。
- PDF 已就绪后的本机检查限15秒前台时间。超时/读取异常给现有重试入口，不归类为 PDF 损坏，也不跳过身份校验。已显示的旧谱可保留；旧检查超时或晚到不能覆盖后来成功的新谱。
- 没有修改业务 schema、数据库迁移、同步协议、网络选路、认证接纳或用户附件，不自动清缓存/重下载。

## 仍需交叉核实

createSessionFetch 的10秒 signal 约束 transport；成功HTTP响应后的 acceptSession/acceptNewSession 仍等待本机 system 事务。故本机存储迟滞可以影响身份就绪，连接健康探测成功并不能排除此路径；实际原因仍待设备证据，交由连接诊断任务交叉检查，不在此PR更改认证安全边界。

PR只提交审查，不合并、不部署。stable提升及第三首发布继续暂停。本次补丁不是对用户设备故障已经消失的保证。

## 联网后暖状态的解释边界

联网打开会确认在线身份、同步乐谱信息/图层，并可能完成自动离线准备；ReaderSession 还会填充乐谱信息内存缓存，解析后的PDF lease在退出后保留15秒、最多保留两份。因此“联网打开后再次离线成功”可能来自身份/快照补全，也可能只是内存暖状态，不能单凭这一点证明冷启动问题已解决或文件曾被删除。

现有浏览器回归中，Chromium实际关闭重启后离线打开通过；WebKit因工具限制使用静态资源在线、API不可达的新页面场景，**没有覆盖真实iOS安装PWA的离线进程冷启动**。受控会话接纳检查另证实：网络响应完成后若acceptSession被阻塞，即使网络deadline信号已abort，请求仍等待acceptance释放；未修改认证代码，该线索供连接任务交叉核实。

## 复审补充：普通目录首次读失败的负缓存

独立复审后继续定位到另一个确定的失败处理问题：首次普通本机目录读取抛错，被 `failed()` 当作空结果发布为已打开目录；离线刷新又直接复用这个结果，不再读取磁盘。隔离回归中，本机目录记录仍在，解除读故障后刷新仍为空；原实现未通过该回归。这能够解释一种“联网恢复后离线也恢复”的路径，但不能证明用户设备实际发生的是这一路径。

本次补充使读取异常进入可重试失败状态，不伪造空目录；页面提供“重试读取”，可直接重读本机，无需联网。首次工作区捕获失败时，重试只重新捕获当前 owner fence，不激活旧身份。身份已换则保持拒绝，原身份恢复后才允许重读。真实不存在目录与存储永久不可用等其他原因不在本次根因结论内。

新增两项核心回归验证普通目录首次读取及工作区捕获失败后离线重试，并检查重试不激活其他身份；新增 Chromium/WebKit 故障注入场景：静态页面正常、API持续断开，首次本机目录读失败显示重试，解除本机故障后同页恢复已保存谱子。浏览器场景是合成故障，不代表已复现真实设备底层异常。所有8项浏览器检查一次通过，未使用重跑消除失败。
